# ТЗ: двухэтапный solver с переносом элиты и сильной мутацией

## Статус

Этот документ описывает **планируемый** режим.

На момент написания режим **ещё не реализован в коде**. Документ фиксирует согласованное поведение до начала реализации.

## Рабочее имя режима

Для краткости в документе новый режим обозначается как:

- `solver_mode = two_stage_restart`

Если при реализации будет выбрано другое имя, логика документа от этого не меняется.

## Назначение режима

Режим нужен для случаев, когда одного запуска обычного `classic` ГА недостаточно, но при этом хочется:

- не делать полностью случайные перезапуски;
- сохранять найденную элиту;
- последовательно встряхивать популяцию;
- после исчерпания потенциала первого этапа переходить ко второму этапу с другими операторами.

Идея режима:

- алгоритм состоит из **серии полных запусков ГА**;
- между запусками сохраняется лучшая особь прошлого запуска;
- остальные особи формируются из финальной популяции прошлого запуска через сильную мутацию;
- первый этап использует фиксированные операторы;
- второй этап использует настраиваемые типы кроссовера и мутации;
- завершение этапов определяется по условию выхода, сравнивающему лучший `difference` соседних запусков.

## Место режима в проекте

Это **новый `solver_mode`**, а не новый `nga_mode`.

Причина:

- текущие `nga_mode` в проекте означают вмешательство внутри одного запуска `classic`;
- новый алгоритм состоит из нескольких полных запусков с передачей состояния между ними;
- по архитектуре он ближе к `restart_rescue`, чем к `staged_hypermutation`.

Следствия:

- режим должен жить рядом с `classic` и `restart_rescue`;
- для этого режима `nga_mode` не используется и должен быть `none`.

## Основные понятия

### Запуск

Под **запуском** понимается один полный прогон ГА со своей начальной популяцией и обычным внутренним циклом поколений.

Один запуск заканчивается по одной из причин:

- `exact_match`
- `stagnation_limit`
- `generation_limit`

### Этап

Режим содержит два этапа:

- этап 1
- этап 2

Каждый этап состоит из последовательности запусков.

### Основная метрика прогресса

Прогресс оценивается только по:

- `difference = abs(target_sum - current_sum)`

Улучшение есть только если:

- `new_difference < old_difference`

Равенство:

- `new_difference == old_difference`

не считается улучшением.

## Условие выхода

У.В. формулируется так:

- лучший `difference` текущего запуска равен лучшему `difference` предыдущего запуска того же этапа.

То есть:

```text
current_run_best_difference == previous_run_best_difference
```

Сравнение идёт:

- на этапе 1 только с предыдущим запуском этапа 1;
- на этапе 2 только с предыдущим запуском этапа 2.

### Почему используется именно `==`

В этом режиме элита переносится в следующий запуск без изменений.

Из-за этого следующий запуск не может начать хуже предыдущего по лучшему известному решению:

- лучшая особь прошлого запуска уже присутствует в новой популяции;
- значит лучший `difference` нового запуска не может стать больше, чем у прошлого запуска.

Поэтому для фиксации отсутствия прогресса достаточно равенства:

- `==`

## Конфигурация режима

Режим использует обычные параметры ГА:

- `population_size`
- `generations`
- `stagnation`
- `crossover_rate`
- `mutation_rate`
- `tournament_size`

И новые параметры режима:

- `solver_mode = two_stage_restart`
- `restart_population_mode`
- `restart_mutation_fraction`
- `stage2_crossover_type`
- `stage2_mutation_type`

### `restart_population_mode`

Параметр нужен для того, чтобы способ построения новой стартовой популяции был **настраиваемым** и расширяемым в будущем.

В первой реализации должен поддерживаться как минимум режим:

- `elite_from_last_population`

Смысл:

- лучшая особь прошлого запуска переносится без изменений;
- остальные особи берутся из финальной популяции прошлого запуска и сильно мутируются.

Даже если на старте будет доступен только один конкретный режим, его нужно выделить как отдельную конфигурацию, а не зашивать в solver-цикл жёстко.

### `restart_mutation_fraction`

Доля битов, инвертируемых при сильной мутации при переходе к следующему запуску.

Диапазон:

- от `0.0` до `1.0`

### `stage2_crossover_type`

Тип кроссовера для запусков этапа 2.

Разрешённые значения на первой реализации:

- `one_point`
- `two_point`

### `stage2_mutation_type`

Тип мутации для запусков этапа 2.

Разрешённые значения на первой реализации:

- `one_point`
- `two_point`

## Валидация конфигурации

Для нового режима конфигурация должна считаться валидной, только если:

- `solver_mode == two_stage_restart`
- `nga_mode == none`
- `generations >= stagnation`
- `restart_mutation_fraction` лежит в диапазоне `0.0..1.0`
- `stage2_crossover_type` входит в допустимый список
- `stage2_mutation_type` входит в допустимый список

## Правило сильной мутации между запусками

Для первой реализации используется следующая схема.

Пусть дана финальная популяция прошлого запуска.

Тогда новая стартовая популяция строится так:

1. Находим лучшую особь прошлого запуска.
2. Переносим её в новую популяцию без изменений.
3. Остальные особи берём из финальной популяции прошлого запуска.
4. Каждую из них подвергаем сильной мутации с долей `restart_mutation_fraction`.
5. Размер новой популяции должен совпадать с `population_size`.

Если лучшая особь встречается в популяции несколько раз, без изменений переносится только один выбранный экземпляр элиты. Все остальные особи, включая возможные дубликаты, проходят сильную мутацию.

### Формула сильной мутации

Для вектора длины `n` и доли мутации `ratio`:

```text
k = min(n, max(1, ceil(ratio * n)))
```

После этого:

- выбираются `k` различных индексов;
- на них инвертируются биты.

## Этап 1

### Операторы этапа 1

На этапе 1 ГА всегда запускается с фиксированными операторами:

- `one_point_crossover`
- `one_point_mutation`

Остальные параметры ГА берутся из общей конфигурации режима.

### Первый запуск этапа 1

Первый запуск этапа 1 стартует с обычной начальной популяции:

- `build_initial_population(...)`

### Поведение после завершения запуска этапа 1

Если запуск этапа 1 завершился по:

- `exact_match`

то весь алгоритм завершается сразу.

Если запуск этапа 1 завершился по:

- `stagnation_limit`

то дальше действует следующая логика:

1. Запоминается лучшая особь запуска.
2. Запоминается лучший `difference` запуска.
3. Если это был первый запуск этапа 1, строится следующий запуск этапа 1.
4. Если это не первый запуск этапа 1, проверяется У.В.
5. Если У.В. не выполняется, строится следующий запуск этапа 1.
6. Если У.В. выполняется, алгоритм переходит в этап 2.

### Что сравнивается на этапе 1

На этапе 1 сравниваются:

- лучший `difference` завершившегося запуска этапа 1;
- лучший `difference` предыдущего запуска этапа 1.

Сравнение идёт именно по лучшему результату **всего запуска**, а не по последнему поколению.

## Переход из этапа 1 в этап 2

Переход в этап 2 происходит тогда, когда после очередного завершённого запуска этапа 1:

- выполнено У.В.

Первый запуск этапа 2 строится из финальной популяции **последнего** запуска этапа 1:

- элита этого запуска переносится без изменений;
- остальные особи сильно мутируются по обычному правилу перехода между запусками.

## Этап 2

### Операторы этапа 2

На этапе 2 используются:

- `stage2_crossover_type`
- `stage2_mutation_type`

На первой реализации это выбор между:

- `one_point`
- `two_point`

При этом:

- `crossover_rate`
- `mutation_rate`
- `population_size`
- `generations`
- `stagnation`
- `tournament_size`

остаются общими параметрами режима и не меняются автоматически между этапами.

### Поведение после завершения запуска этапа 2

Если запуск этапа 2 завершился по:

- `exact_match`

то весь алгоритм завершается сразу.

Если запуск этапа 2 завершился по:

- `stagnation_limit`

то дальше действует следующая логика:

1. Запоминается лучшая особь запуска.
2. Запоминается лучший `difference` запуска.
3. Если это был первый запуск этапа 2, строится следующий запуск этапа 2.
4. Если это не первый запуск этапа 2, проверяется У.В. относительно предыдущего запуска этапа 2.
5. Если У.В. не выполняется, строится следующий запуск этапа 2.
6. Если У.В. выполняется, весь алгоритм завершается.

### Что сравнивается на этапе 2

На этапе 2 сравниваются:

- лучший `difference` завершившегося запуска этапа 2;
- лучший `difference` предыдущего запуска этапа 2.

Сравнение с последним запуском этапа 1 на этапе 2 **не используется**.

## Поведение при `generation_limit`

Отдельный запуск нового режима теоретически всё ещё может завершиться по:

- `generation_limit`

Правило валидации:

- `generations >= stagnation`

нужно для запрета явно некорректной конфигурации, но само по себе не гарантирует, что внутри конкретного запуска обязательно будет достигнута стагнация: до лимита поколений могут продолжаться улучшения.

Поэтому для полноты спецификации фиксируется следующее правило:

- если любой запуск нового режима завершился по `generation_limit`, весь алгоритм завершается немедленно с `stop_reason = generation_limit`.

То есть:

- `generation_limit` не игнорируется;
- дополнительные запуски после него не выполняются.

## Итоговые причины остановки

Во внешнем результате нового solver-режима должны использоваться причины:

- `exact_match`
- `stagnation`
- `generation_limit`

Смысл:

- `exact_match` если в любом запуске найдено точное решение;
- `generation_limit` если какой-либо запуск завершился по лимиту поколений;
- `stagnation` если алгоритм завершился на этапе 2 по У.В. без точного решения.

Отдельный специальный `stop_reason` для перехода между этапами или для У.В. не нужен.

## Состояние, которое нужно хранить

Во время работы нового режима нужно хранить:

- текущую популяцию активного запуска;
- лучшую особь активного запуска;
- лучший `difference` активного запуска;
- общее число использованных поколений;
- номер текущего этапа;
- число запусков этапа 1;
- число запусков этапа 2;
- историю лучших `difference` по запускам этапа 1;
- историю лучших `difference` по запускам этапа 2;
- флаг, был ли выполнен переход в этап 2.

## Что должно попасть в результат

Во внешний результат нового solver-режима нужно добавить или заполнить:

- `generations_used` как суммарное число поколений по всем запускам;
- `stage1_run_count`
- `stage2_run_count`
- `stage2_used`
- `stage1_best_differences`
- `stage2_best_differences`

Также во внешнем результате должны остаться обычные поля:

- `best_vector`
- `best_sum`
- `fitness`
- `difference`
- `exact_match`
- `stop_reason`

## Полная схема алгоритма

```text
stage = 1
stage1_history = []
stage2_history = []
total_generations = 0

run stage 1 with initial random population

while true:
    execute current GA run
    total_generations += run.generations_used

    if run.stop_reason == exact_match:
        return exact_match

    if run.stop_reason == generation_limit:
        return generation_limit

    if stage == 1:
        append run.best_difference to stage1_history

        if len(stage1_history) == 1:
            build next stage 1 population from final population of this run
            run next stage 1
            continue

        if stage1_history[-1] == stage1_history[-2]:
            stage = 2
            build first stage 2 population from final population of this run
            run first stage 2
            continue

        build next stage 1 population from final population of this run
        run next stage 1
        continue

    if stage == 2:
        append run.best_difference to stage2_history

        if len(stage2_history) == 1:
            build next stage 2 population from final population of this run
            run next stage 2
            continue

        if stage2_history[-1] == stage2_history[-2]:
            return stagnation

        build next stage 2 population from final population of this run
        run next stage 2
```

## Что не входит в первую реализацию

Пока в первую реализацию не входят:

- автоматическое изменение `mutation_rate` между этапами;
- автоматическое изменение `crossover_rate` между этапами;
- автоматическое изменение `population_size` между этапами;
- разные стратегии построения следующей популяции для этапа 1 и этапа 2;
- использование нескольких элит вместо одной;
- отдельные пользовательские пресеты по стадиям.

## Будущие расширения

Режим должен быть написан так, чтобы позже можно было без переписывания основной логики добавить:

- другие режимы `restart_population_mode`;
- разные стратегии построения новой популяции для этапов 1 и 2;
- несколько сохраняемых элит;
- отдельные коэффициенты сильной мутации для разных этапов;
- дополнительные типы мутации и кроссовера на этапе 2.
